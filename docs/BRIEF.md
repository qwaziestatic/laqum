Product in one paragraph

Drivers in Addis Ababa use a mobile app to find nearby parking lots (hotels, dedicated lots), see live free-slot counts, book a slot with a small deposit, navigate there, and check in and out with a QR code. Parking attendants use a web dashboard that shows each lot as a grid of top-down car slots, colored by live status. Attendants register walk-in cars, scan QR codes at entry and exit, and record cash. Drivers pick how long they'll stay; overstays are billed at a separate rate. Slots are held for a limited time; a no-show forfeits the deposit.

-- ─── What the dashboard grid reads ───────────────────────────────────────
-- Slot status is DERIVED from bookings, never stored on the slot.
CREATE VIEW slot_status AS
SELECT
  s.id AS slot_id, s.lot_id, s.label, s.zone, s.grid_row, s.grid_col, s.app_bookable, s.in_service,
  CASE
    WHEN NOT s.in_service                            THEN 'out_of_service'
    WHEN b.status IN ('PENDING_PAYMENT', 'RESERVED') THEN 'reserved'
    WHEN b.status = 'CHECKED_IN'                     THEN 'occupied'
    WHEN b.status = 'OVERSTAY'                       THEN 'overstay'
    ELSE 'free'
  END AS display_status,
  b.id AS booking_id, b.source, b.vehicle_plate, b.hold_expires_at, b.planned_end_at, b.updated_at
FROM slots s
LEFT JOIN bookings b
  ON b.slot_id = s.id
 AND b.status IN ('PENDING_PAYMENT', 'RESERVED', 'CHECKED_IN', 'OVERSTAY');

Notes on the schema:

Marking a slot out of service is rejected with 409 SLOT_IN_USE while it has a live booking. The view still handles the combination defensively, and the staff UI must always show a slot's live booking and allow checkout.
A driver with a CHECKED_OUT (unpaid) booking may not create a new one. This is enforced in application code, using bookings_unpaid_by_user.

"Live" statuses = PENDING_PAYMENT, RESERVED, CHECKED_IN, OVERSTAY. Put this list in exactly one place in packages/shared and derive everything from it.

Booking state machine (fixed)
From	To	Trigger	Actor
(new, app)	PENDING_PAYMENT	Driver books; deposit > 0	driver
(new, app)	RESERVED	Driver books; deposit = 0	driver
PENDING_PAYMENT	RESERVED	Deposit confirmed	system (webhook/verify)
PENDING_PAYMENT	EXPIRED	Payment window lapses	job
RESERVED	CHECKED_IN	Entry QR / short code scanned	attendant
RESERVED	EXPIRED	Hold window lapses; deposit kept	job
RESERVED	CANCELLED	Driver cancels; deposit kept	driver
(new, walk_in)	CHECKED_IN	"Walk-in park" on a free slot	attendant
CHECKED_IN	OVERSTAY	planned_end_at passes	job
CHECKED_IN, OVERSTAY	CHECKED_OUT	Exit scan or manual release	attendant
CHECKED_OUT	PAID	Final payment succeeds, cash recorded, or amount due = 0	system / attendant

Every other transition is illegal and must be rejected with a typed error.

Invariants (the core of the system; test every one)
No double booking. Enforced by the partial unique index one_live_booking_per_slot. Booking creation is a plain INSERT, and a unique violation maps to HTTP 409 SLOT_TAKEN. Never do "check then insert" in application code.
One live booking per driver. Enforced by one_live_booking_per_user. Additionally, the API refuses new bookings from a driver with an unpaid CHECKED_OUT booking (OUTSTANDING_BALANCE).
All status changes go through one function, transition(bookingId, from, to, actor, patch), implemented as a compare-and-set: UPDATE bookings SET status = $to, ... WHERE id = $id AND status = ANY($allowedFrom) RETURNING * Zero rows returned means someone else won the race, which maps to 409 STATE_CONFLICT. The same DB transaction inserts the booking_events row. No code anywhere else may write bookings.status. Add a lint rule or a test that greps for violations.
Slot status is derived from live bookings via slot_status. No status column on slots.
Side effects happen after commit. Socket emits, push notifications, and job scheduling run only after the transaction commits.
Jobs are idempotent. Every job calls transition(). If the booking has already moved on, the job is a no-op.
Realtime is a notification channel, not a source of truth. Clients refetch a snapshot over REST on connect and reconnect, then apply events. Every event carries the booking's updated_at or a version so clients can drop stale events.
Business rules
Slot assignment: the driver chooses a lot, not a slot. The server assigns a free slot where app_bookable = true and in_service = true, ordered by (zone, grid_row, grid_col). On a unique violation, retry the next free slot up to 3 times before returning LOT_FULL.
Distance check at booking: the client sends its current coordinates. The server computes haversine distance to the lot and rejects the booking if it exceeds max_booking_distance_m (TOO_FAR). Use no paid routing API in the MVP.
Windows: PENDING_PAYMENT holds for payment_window_minutes. On entering RESERVED, set hold_expires_at = now() + hold_minutes.
Planned duration: planned_minutes must be a positive multiple of block_minutes. planned_end_at is set at check-in: checked_in_at + planned_minutes.
Extension: allowed only while CHECKED_IN and before planned_end_at, in whole blocks. It updates planned_minutes and planned_end_at and reschedules the overstay job.
Billing is a pure function in packages/shared, computeBill(booking, lot, checkoutAt), returning an itemized breakdown:
App bookings: planned_blocks × rate + ceil(overstay_minutes / block_minutes) × overstay_rate − deposit_paid, floored at 0. There is no refund for early exit.
Walk-ins: ceil(actual_minutes / block_minutes) × rate, with a minimum of 1 block. Walk-ins have no planned end and never enter OVERSTAY.
Unit-test boundaries exhaustively: exactly on the minute, one minute over, zero-length stays, and deposit greater than the bill.
Checkout: compute the bill and set amount_due_santim. If it's 0, transition straight to PAID. Otherwise the driver pays in-app (Chapa) or the attendant records cash.
Deposits are kept on EXPIRED and CANCELLED. Refunds exist only as an operator-initiated correction (payment_kind = 'refund'), not in any automatic flow.
Payments
Define a PaymentProvider interface (initialize, verify, refund). Implement ChapaProvider (test mode) and FakePaymentProvider (dev and tests; payments auto-succeed after a configurable delay).
Chapa flow: initialize with our own unique tx_ref, return the checkout URL, and receive the webhook. Never trust a webhook body alone. Always confirm with Chapa's verify endpoint before transitioning, and validate the webhook signature exactly as Chapa's current docs specify.
Webhook handling is idempotent through the unique tx_ref. Duplicate deliveries must be harmless.
Store the raw verify response in provider_payload.
Cash is recorded by an attendant (recorded_by required).
Scheduled jobs (BullMQ)
expire-hold (delayed to hold_expires_at): PENDING_PAYMENT or RESERVED to EXPIRED.
mark-overstay (delayed to planned_end_at): CHECKED_IN to OVERSTAY.
time-reminder (10 minutes before planned_end_at): push notification only.
Use deterministic job IDs (expire-hold:{bookingId}) so rescheduling replaces the old job.
A sweeper runs every minute and applies any overdue expiry or overstay the delayed jobs missed (for example, if Redis was flushed). It's the safety net; the delayed jobs are the fast path.
Auth
Phone number + OTP. OTPs are 6 digits, stored hashed, expire in 5 minutes, allow at most 5 attempts, and are rate-limited per phone and per IP.
Hide SMS behind an SmsProvider interface. Implement only ConsoleSmsProvider (logs the code) for now; a real provider comes later.
Short-lived JWT access token plus a rotating refresh token (stored hashed, revocable).
Roles: driver, attendant, operator_admin. Staff endpoints also check lot_staff membership for the specific lot.
Socket.io handshake is authenticated with the same JWT.
